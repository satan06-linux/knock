# Ultron Implementation Roadmap

Product vision: Ultron is a workspace-first, local-first terminal coding agent. A developer installs it once, runs `ultron` from any project folder, and uses the interactive session to understand, build, test, debug, review, and hand off software changes safely.

Command philosophy:
- External entry points stay simple: `ultron` and `ultron --help`.
- All work happens inside the interactive Ultron session through natural-language requests and slash commands.
- `ultron` always starts in the current terminal folder.
- Ultron only reads or edits the active workspace unless the user explicitly searches for and selects another workspace.

====================================================================
PHASE 0 - STABILIZE THE CORE
====================================================================

Goal: Make Ultron safe, reliable, and dependable before expanding its features.

Workstream 1 - Path safety, argument validation, and REPL fixes

1. Workspace containment
   - Resolve all paths with realpath(abspath(...)).
   - Use commonpath with Windows case normalization.
   - Reject different-drive comparisons and catch ValueError safely.
   - Block sibling-directory, traversal, symlink, and junction escapes.
   - Apply the same containment logic to tools, context pinning, checkpoints, and workspace switching.

2. Sensitive-file policy
   - Deny explicit workspace-relative patterns: .git/**, .env, .env.*, and configurable credential patterns.
   - Keep the policy configurable per project later; never use an overly broad filename rule that blocks normal application files.

3. Tool-call validation
   - Validate the required keys and types of every model-issued tool call before execution.
   - Reject malformed arguments with a clear tool-result error; never replace invalid arguments with defaults.
   - Validate paths, command strings, line numbers, patch fields, and Git commit messages.

4. REPL fixes
   - Fix the missing Confirm import used by /commit.
   - Add regression tests for every built-in slash command.

Workstream 2 - Execution, streaming, and safe Git

1. Command execution
   - Make shell timeout configurable; default to 180 seconds.
   - Keep the first 3,000 and last 3,000 characters of stdout and stderr, preserving exit code and a truncation marker.
   - Support clean cancellation and never send unlimited logs into the model context.

2. Ollama reliability
   - Use HTTPX streaming context management for true live token rendering.
   - Close streams safely on interruption.
   - Match installed model names strictly.
   - Add configurable temperature, context size, and keep-alive settings.

3. Git safety
   - Never initialize a Git repository implicitly.
   - Stage with `git add -- <pathspec>`; never use `git add -A` for agent commits.
   - Show staged, unstaged, and untracked changes in /diff.
   - Calculate the empty tree dynamically for repositories without HEAD.
   - Before editing a dirty file, require explicit user approval.
   - If a dirty file is approved for editing, disable automatic committing of that file until the user separates their existing work through a commit, stash, or explicit checkpoint.

4. Checkpoint and undo
   - Capture a file checkpoint immediately before its first mutation in a task.
   - Store checkpoints outside the workspace, atomically and with restricted permissions.
   - Record original state, whether the file existed, mode, and post-edit hash.
   - /undo restores only files that still match Ultron's last-written hash.
   - If a user changed a file afterwards, stop, show a conflict diff, and ask what to do.
   - Delete an Ultron-created file only if it still matches its recorded post-edit hash.

Workstream 3 - Context and test hardening

1. Bounded context
   - Cap pinned content at 50,000 characters.
   - Cap workspace-tree output at 200 lines.
   - Trim message history only by complete user/assistant/tool turn groups.
   - Maintain an older-history summary capped at 2,000 characters.

2. Tests
   - Mock Ollama responses for deterministic CI tests.
   - Move live Ollama checks to an optional test that skips cleanly when unavailable.
   - Add path-escape, symlink/junction, multi-drive, dirty-file, malformed-tool, Git, checkpoint, and REPL smoke tests.

Acceptance criteria:
- No file operation escapes the selected workspace.
- Bad tool calls do not execute.
- User edits are not silently staged, committed, or overwritten.
- /undo is conflict-aware.
- CLI commands work without a live Ollama server in the ordinary test suite.

====================================================================
PHASE 1 - FAST EVERYDAY CODING
====================================================================

Goal: Make Ultron fast and pleasant for a developer's daily project work.

1. Workspace-first startup
   - Running `ultron` starts in the terminal's current folder.
   - Show workspace path, detected project type, Git branch, changed-file count, active model, and context usage.
   - Support /workspace, /tree, /refresh, /status, /logs, /last-error, /repeat, and /cancel.

2. Project onboarding
   - Add /onboard to detect languages, frameworks, entry points, package managers, test/lint/format/build commands, database use, and local run instructions.
   - Save only verified project facts as project memory.
   - Clearly mark inferred setup guidance as unverified.

3. Command intelligence
   - Detect common project commands from package files, Makefiles, task runners, and project configuration.
   - Suggest the smallest relevant test, lint, type-check, or build command after a change.
   - Ask before dependency installation, migrations, network access, server launch, or destructive operations.

4. Core coding workflow
   - /plan <task>: read-only file-impact plan and verification plan.
   - /tasks: visible checklist with planned, editing, testing, and verified states.
   - /test [target], /lint [target], and /fix for focused repair loops.
   - /checkpoint <name> and /undo for safe recovery.
   - End every task with a smart work summary: files changed, commands run, evidence, warnings, and unverified items.

Acceptance criteria:
- A developer can open an unfamiliar project, discover how to run it, make a small feature change, and verify it without manually finding every command.

====================================================================
PHASE 2 - PROJECT INTELLIGENCE
====================================================================

Goal: Help Ultron understand an unfamiliar codebase before it changes it.

1. Workspace discovery and switching
   - /analyze without a folder analyzes the active workspace recursively.
   - /find-folder <name> searches the workspace first.
   - If not found, ask before read-only searching available drives.
   - Display numbered matches with full paths; never choose or switch automatically.
   - /open <number-or-path> changes workspace only with explicit user confirmation and resets task/context state.
   - Skip .git, dependencies, virtual environments, build output, caches, and protected system folders when searching.

2. Repository map and navigation
   - Build a compact map of packages, entry points, symbols, imports, tests, services, and dependencies.
   - Add /find, /symbol, /references, /flow, and /explain.
   - Present evidence and source paths for every architecture claim.

3. Impact analysis
   - Add /impact <file-or-symbol>.
   - Show callers, imports, related tests, schemas, routes, database impact, public API risk, and likely regression areas.
   - Require an impact summary before broad refactors or public-contract changes.

4. Failure investigator
   - Add /why to analyze the latest test, build, or runtime error.
   - Extract the meaningful exception and source location from long logs.
   - Propose minimal reproductions, likely root cause, target files, and safe repair options.
   - Add /min-repro to create a focused regression test or reproducible script.

5. Project memory and conventions
   - Add editable project instructions through ULTRON.md and structured settings through .ultron.toml.
   - Save verified conventions, successful commands, architecture notes, and known pitfalls.
   - Study similar existing code before scaffolding a new feature, so generated code matches the repository style.

Acceptance criteria:
- Ultron can explain how a feature works, locate related code/tests, assess change impact, and diagnose a normal test failure with evidence.

====================================================================
PHASE 3 - SAFE AUTONOMOUS ENGINEERING
====================================================================

Goal: Let Ultron complete multi-step coding tasks while keeping developer control.

1. Intent modes
   - /ask: inspection and explanation only.
   - /plan: read-only implementation planning.
   - /build: implementation with approval policy.
   - /fix: controlled test-failure repair loop.
   - /review: inspect changes without editing.

2. Change contracts and budgets
   - Before implementation, record goal, required preserved behavior, new behavior, expected files, and verification steps.
   - Show expected change scope.
   - Pause for approval if a task begins touching substantially more files or systems than planned.

3. Verification gate
   - Add /verify.
   - Run or propose focused tests, full suite when appropriate, lint, formatting, type check, build, secret scan, and diff review.
   - Report Passed, Failed, Not run, and Skipped by user separately.
   - Never claim a task is verified without command evidence.

4. Senior-style review
   - Review the current diff for bugs, security issues, authorization gaps, performance concerns, API breaks, missing tests, dead code, and duplication.
   - Give findings a severity, location, explanation, and suggested fix.

5. Refactor and regression safeguards
   - /impact before risky refactors.
   - Find references and protect public contracts.
   - Add test-gap detection for changed behavior without a matching test.
   - Add flaky-test detection and /bisect guidance for regressions.
   - Add /reproduce to save a sanitized bug reproduction, relevant logs, fix, and verification results.

6. Evidence-first execution
   - Mark conclusions as Observed from code, Verified by command, Inferred, or Not verified.
   - Prefer minimal diffs and ask one concise question when requirements are genuinely ambiguous.

Acceptance criteria:
- Ultron can plan, implement, test, review, and summarize a multi-file feature without exceeding the agreed change scope or hiding unverified work.

====================================================================
PHASE 4 - PROFESSIONAL PROJECT DELIVERY
====================================================================

Goal: Support team-quality code delivery and reliable project-building workflows.

1. Professional Git workflow
   - Offer isolated branches or worktrees for risky work.
   - Add /pr-summary with title, change summary, test evidence, risks, migration notes, and reviewer checklist.
   - Add commit-quality checks: focused diff, no debug leftovers, matching tests, and accurate conventional commit messages.

2. Monorepo and multi-project support
   - Detect packages, services, shared libraries, and dependency relations.
   - Ask which package is active when a request is ambiguous.
   - Run targeted commands instead of unnecessary whole-monorepo checks.
   - Add /recent and configurable workspace aliases; one workspace remains active at a time.

3. Project-building assistant
   - Add /feature <description> to produce a vertical-slice plan: models, APIs, services, UI, tests, migration, and docs.
   - Add scaffold auditing to ensure exports, registrations, tests, configuration, migrations, and documentation are not forgotten.
   - Add API contract checks, migration/rollback planning, feature-flag support, and environment /doctor diagnostics.

4. Documentation and handoff
   - Add /docs-check to identify README, API docs, config examples, changelog, and migration notes affected by code changes.
   - Add /handoff to generate a developer-ready report: changed files, decisions, commands, tests, risks, limitations, and next steps.
   - Add a decision log and task replay that preserve the task's plan, tool actions, diffs, and evidence.

5. CI and extensibility
   - Add a future headless JSON mode for CI, always requiring an explicit workspace path.
   - Add coding-focused integrations only: source hosting, issue trackers, documentation lookup, package audit, browser testing, and developer tools.
   - Add plugins/skills and hooks only after the core permission model is mature.

6. Health and quality analysis
   - Detect unused dependencies, duplicate logic, likely dead code, N+1 query patterns, blocking operations in async code, repeated network calls, and configured package vulnerabilities.
   - Add a release-readiness checklist for versions, migrations, tests, builds, changelog, and compatibility.

Acceptance criteria:
- Ultron can safely prepare a feature branch or worktree, validate a project-level change, produce PR-ready evidence, and hand work to another developer.

====================================================================
PRIORITY ORDER
====================================================================

1. Finish all Phase 0 work and tests before adding new capability.
2. Build Phase 1 onboarding, command intelligence, plan/test/fix workflow, and summaries.
3. Build Phase 2 project mapping, /why, /impact, and convention-aware context.
4. Build Phase 3 verification, review, change contracts, and regression safeguards.
5. Build Phase 4 worktrees, PR handoff, monorepo support, CI, and coding-focused extensions.

The product must remain focused on software development. Every feature should make it faster, safer, clearer, or more verifiable to understand, build, debug, test, review, and deliver code.
