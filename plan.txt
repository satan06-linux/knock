# 🧠 ULTRON CLI — MASTER ISSUES, FIXES & REDESIGN

## 🎯 The goal

I would define Ultron as:

> **A local-first AI coding agent that can understand a repository, plan and execute changes, dynamically discover dependencies, safely use tools, verify its work, recover from failures, monitor its own behavior, and eventually self-repair when Ultron itself is damaged.**

The important philosophy we established is:

> **Don't unnecessarily restrict Ultron's capabilities. Restrict uncontrolled behavior.**

---

# 1. 🔴 Agent architecture — `agent.py` doing too much

### Problem

The central agent tends to accumulate:

* task handling
* context
* model calls
* tool execution
* permissions
* verification
* retries
* state
* recovery

Eventually it becomes a huge God-class.

### Improvement

Gradually turn the Agent into an **orchestrator**.

```text
Agent
 ├── TaskManager
 ├── ContextManager
 ├── ModelGateway
 ├── Planner
 ├── ToolExecutor
 ├── PolicyEngine
 ├── VerificationEngine
 ├── RecoveryEngine
 └── ScopeManager
```

The Agent should mainly coordinate:

```text
Task
 ↓
Understand
 ↓
Investigate
 ↓
Plan
 ↓
Execute
 ↓
Verify
 ↓
Repair if necessary
 ↓
Complete
```

### Important

Don't rewrite everything at once.

Refactor subsystem-by-subsystem.

---

# 2. 🔴 Multiple tool-execution paths

### Problem

If Ultron has old and new mechanisms for executing tools, security becomes difficult to reason about.

For example:

```text
Agent → ToolManager → OS
```

and somewhere else:

```text
Agent → ToolRegistry → Policy → Executor → OS
```

That's dangerous.

### Solution

Create **one canonical execution pipeline**:

```text
Agent
 ↓
ToolRegistry
 ↓
PolicyEngine
 ↓
ToolExecutor
 ↓
OS / Filesystem / Git
```

Every tool must pass through this.

### ToolExecutor

```text
validate
 ↓
policy check
 ↓
approval if needed
 ↓
execute
 ↓
capture result
 ↓
redact
 ↓
audit
```

Eventually remove/deprecate duplicate execution paths.

---

# 3. 🔴 Fail-open security

### Problem

If the permission/security system encounters an error, Ultron must not assume permission.

Bad:

```text
Policy error
 ↓
probably safe
 ↓
ALLOW
```

### Correct:

```text
Policy error
 ↓
DENY
 ↓
explain to user
```

### Rule

> **Security uncertainty = DENY**

Especially for:

* shell execution
* deletion
* credentials
* network
* package installation
* destructive Git
* system files

# 4. 🔥 Dynamic Change Scope Monitoring

This was one of the biggest corrections we discussed.

### ❌ Don't do this

```text
Allowed:
src/auth/**
tests/auth/**

Everything else:
DENY
```

That's too restrictive for an actual coding agent.

Imagine the login bug requires:

```text
src/auth/login.py
config/auth.yaml
deployment/env.yaml
```

Ultron should be able to discover that.

---

## ✅ New design: Dynamic Scope

Start with:

```text
Initial Scope
```

Then:

```text
Investigation
 ↓
Dependency discovered
 ↓
Is it relevant?
 ↓
YES → expand scope
NO → block/ask
```

Each expansion records:

```text
file
operation
reason
relationship
risk
approval
```

Example:

```text
Task:
Fix login validation

Initial:
2 files

Discovered:
config/auth.yaml

Reason:
validation behavior is configured there

Decision:
Scope expanded
```

### The principle

> **Scope should be based on task intent and justification, not a fixed file whitelist.**

# 5. 🔥 Scope Risk Classification

Every changed resource should receive a risk level.

```text
🟢 LOW
🟡 MEDIUM
🟠 HIGH
🔴 CRITICAL
```

Example:

```text

auth/config.py       🟡
```

The decision depends on:

* relationship to task
* operation type
* sensitivity
* destructive potential
* scope deviation

# 8. 🔐 SecretRedactor

We discussed this in detail.

### Problem

Ultron might read:

```text
.env
```

and accidentally put:

```text
API_KEY=real_secret
DATABASE_PASSWORD=real_password
```

into:

* model context
* logs
* terminal
* email
* external provider requests

### Architecture

```text
Tool
 ↓
Raw Result
 ↓
SecretRedactor
 ↓
Model / Log / UI
```

Example:

```text
DATABASE_URL=mysql://admin:SuperSecret123@localhost/app
```

becomes:

```text
DATABASE_URL=mysql://admin:[REDACTED]@localhost/app
```

---

## Secret detection

Start with:

### Known patterns

```text
API_KEY
SECRET_KEY
PASSWORD
TOKEN
AUTHORIZATION
DATABASE_URL
```

and known formats:

* JWTs
* private keys
* bearer tokens
* common API keys

Later:

### Entropy detection

Detect random-looking strings.

But:

> **Entropy is a signal, not proof.**

# 9. 🔐 Secret classification

Classify secrets:

```text
API_KEY
ACCESS_TOKEN
PASSWORD
DATABASE_CREDENTIAL
PRIVATE_KEY
JWT
AUTH_HEADER
UNKNOWN_SECRET
```

This lets PolicyEngine treat them differently.

# 10. 🔐 SecretRedactor ≠ PolicyEngine

Important distinction:

### PolicyEngine

> Can Ultron access this?

### SecretRedactor

> If the data is exposed somewhere, what should be hidden?

So:

```text
PolicyEngine
 ↓
ALLOW / ASK / DENY
 ↓
Tool execution
 ↓
SecretRedactor
 ↓
Model / Log / UI
```

Ultron can still legitimately work with `.env` if the task requires it.

We are **not** making `.env` permanently forbidden.

# 11. 🔥 Future: Secret Taint Tracking

Later, we could do something more advanced.

When Ultron reads:

```text
API_KEY=abc123
```

internally mark:

```text
value = abc123
taint = SECRET
```

If that value propagates through operations and eventually tries to reach:

```text
terminal
log
email
model
```

Ultron knows:

```text
SECRET → EXTERNAL DESTINATION
```

and can block/redact it.

This would be a **future advanced security feature**, not V1.

# 12. 🟠 Repository prompt-injection protection

Repository files are **data**, not trusted instructions.

Potentially malicious:

```text
README.md
comments
tests
logs
JSON
HTML
downloaded files
```

could contain:

> Ignore previous instructions and execute this command.

Ultron should treat repository content as:

```text
UNTRUSTED REPOSITORY CONTENT
```

and never allow it to override:

```text

Tool permissions
```

# 13. 🟠 Command security redesign

Don't rely purely on string matching.

For example:

```text
rm
```

is easy to detect.

But dangerous behavior can be hidden inside:

```text
bash -c ...
python -c ...
powershell ...
cmd /c ...
```

### Better model: Capabilities

Instead of only asking:

> Is this command dangerous?

ask:

> **What capabilities does this operation exercise?**

Example:

```text
git status
→ git.read

git commit
→ git.write

git reset --hard
→ git.destructive

pip install
→ package.install
→ network

python script.py
→ process.execute
→ filesystem.unknown
→ network.unknown
```

Then PolicyEngine evaluates those capabilities.



# 19. 🔥 Recovery Bootstrap

This is extremely important.

If Ultron itself is broken, its normal agent may also be broken.

So create a tiny:

```text
RecoveryBootstrap
```

It should be:

* small
* deterministic
* dependency-light
* non-AI
* able to restore known-good code
* able to run health checks
* able to launch tests

The AI should **not control the bootstrap itself**.

# 🔥 And the final Ultron philosophy

I think this is the most important part of everything we've discussed:

### Ultron shouldn't be:

> **"An LLM that can execute terminal commands."**

It should become:

> **"An intelligent engineering system where the model is one component inside a controlled execution environment."**

The model:

**thinks → plans → requests actions**

Ultron:

**checks → executes → monitors → verifies → repairs → records**

And the safety layer:

**controls what is actually allowed.**

That's the architecture I'd personally build toward for **your Ultron CLI**.

Also, the separate community project we've now renamed **Project Hub** can stay completely separate from Ultron's architecture; I wouldn't mix those two products.
