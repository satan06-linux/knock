================================================================================
           ULTRON CLI - PHASE 0 (STABILIZE THE CORE) REPORT
================================================================================

This document details the complete step-by-step engineering, implementation,
and verification procedures executed for Phase 0 stabilization of the Ultron CLI.

--------------------------------------------------------------------------------
1. SECURITY & CONTAINMENT CONTROLS (PATH CONTAINMENT & SENSITIVE PATHS)
--------------------------------------------------------------------------------
To prevent workspace escapes via sibling paths, Windows drive mismatches,
or symlinks/junctions:
* Created: `ultron/security.py` containing `validate_path(path, workspace_root)`.
* How it works:
  - Resolves target paths using `os.path.realpath` to resolve symlinks and junctions.
  - Normalizes casing of paths (crucial on Windows).
  - Uses `os.path.commonpath` to ensure the resolved target path is nested
    within the workspace root directory.
  - Detects Windows drive letters: throws a PermissionError if target drive
    mismatches the workspace drive.
  - Implements a root-relative sensitive file pattern deny list (.git/**, .env, 
    .env.*, **/*credential*).
  - Validates hosts files: allows a file named 'hosts' inside the workspace, 
    but blocks system files such as 'C:\Windows\System32\drivers\etc\hosts'.
* Integrated into:
  - `ultron/tools.py` (`_resolve_safe_path` calls `validate_path`).
  - `ultron/context.py` (`add_file` validates paths prior to pinning).

--------------------------------------------------------------------------------
2. MALFORMED TOOL ARGUMENT VERIFICATION
--------------------------------------------------------------------------------
To block incorrect types or schemas generated by local models:
* Implemented: `validate_tool_args(name, args)` inside `ultron/agent.py`.
* How it works:
  - Checks if the model returned dictionary arguments (returns error if string).
  - Validates existence and type of required fields for `view_file`, `write_file`,
    `patch_file`, `run_command`, `git_commit`, etc.
  - Aborts execution if schema validation fails and returns the exact validation
    error message to the model's chat history so it can correct itself.

--------------------------------------------------------------------------------
3. SAFE GIT WORKFLOWS & AUTOCCOMMIT PROTECTION
--------------------------------------------------------------------------------
To prevent staging unintended changes and handling unborn repositories:
* Scoped commits: In `ultron/tools.py`, `git_commit` uses `git add -- <pathspec>`
  to restrict staged additions to exactly the modified files, preventing pathspec
  options hijack.
* Unborn repository diffing:
  - Created `get_empty_tree_hash` in `ultron/tools.py`.
  - It pipes empty bytes (`input=b""`) to `git hash-object -t tree --stdin` to resolve the
    empty tree hash dynamically, adapting to SHA-1 or SHA-256 repositories.
  - Used in `/diff` and `/commit` to retrieve clean diffs when no Git HEAD exists.
* Dirty-File Guard:
  - Checks if a target file is dirty at task start using `git status --porcelain -- <file>`.
  - Refuses to edit the file unless the user confirms.
  - If approved, adds the file to `self.pre_dirty_files` to bypass all automatic
    task autocommits, ensuring pre-existing edits are not silently committed.

--------------------------------------------------------------------------------
4. CONFLICT-AWARE CHECKPOINT & /UNDO MANAGER
--------------------------------------------------------------------------------
To ensure changes can be cleanly rolled back:
* Created: `ultron/checkpoint.py` with `CheckpointManager`.
* How it works:
  - Stores checkpoints in `~/.ultron/checkpoints/<project_hash>/`.
  - Restricts folder permissions to owner read-write (mode 0o700 / 0o600).
  - Backs up original file content and file permissions mode atomically BEFORE
    the first mutation of each file in a task.
  - Records the post-edit SHA-256 hash of mutated files.
  - When the user triggers `/undo`:
    - Compares current file hashes with recorded post-edit hashes.
    - If hashes match (no user changes since task completion), restores files or
      deletes newly created files safely.
    - If a conflict is detected (user modified the file after Ultron), aborts and
      asks the user if they want to force overwrite or preserve their changes.

--------------------------------------------------------------------------------
5. CONTEXT BUDGET & TURN-AWARE HISTORY COMPRESSION
--------------------------------------------------------------------------------
To control context window usage:
* Directory tree: Cap `get_workspace_tree()` output in `ultron/context.py` at 200 lines.
* Pinned files: Cap pinned context content budget at 50,000 characters.
* History Trim & Compression:
  - Implemented `get_trimmed_history_messages(max_turns=12)` in `ultron/agent.py`.
  - Groups messages by full turns (User -> Assistant -> Tool Call -> Tool Result).
  - Keeps only the last 12 complete turns.
  - Compresses older message history using Ollama into a dense summary limited
    strictly to 2,000 characters, prepend it to active system memory.

--------------------------------------------------------------------------------
6. VERIFICATION & TEST SYSTEM
--------------------------------------------------------------------------------
We created and verified the following test suites:

* Unit tests (`tests/test_agent.py`):
  - Validates safe path containment.
  - Verifies read/write/patch operations.
  - Validates ContextManager.

* Mocked integration tests (`tests/verify_agent.py`):
  - Headless-friendly execution by patching `ultron.repl.PromptSession` (bypassing
    Win32 screen buffer errors).
  - Windows-friendly double-quoted shell arguments.
  - Verifies:
    1. Workspace path escapes (traversal, drives, deny lists).
    2. Dirty-file autocommit bypass.
    3. Conflict-aware `/undo` prompt and skip logic.
    4. Malformed tool argument validation and rejection.
    5. Slash commands completeness check (`/help`, `/diff`, `/commit`, `/undo`).

* Live tests (`tests/live_integration_test.py`):
  - Runs against a live local Ollama server if available, testing real-world LLM
    responses, tool executions, and Git autocommits. Skips cleanly if offline.

All tests ran successfully with OK status (exit code 0).

           ULTRON CLI - PHASE 1 (FAST EVERYDAY CODING) REPORT

This section details the complete step-by-step engineering, implementation,
and verification procedures executed for Phase 1 (Fast Everyday Coding) of the Ultron CLI.

--------------------------------------------------------------------------------
1. STARTUP STATUS DASHBOARD & WORKSPACE STATS
--------------------------------------------------------------------------------
To display the workspace status immediately upon starting or running `/status` or `/workspace`:
* Implemented: `get_status_dashboard()` in `ultron/agent.py` and `get_git_info()`, `detect_project_type()` in `ultron/tools.py`.
* How it works:
  - Retrieves active git branch and modified files count.
  - Detects project type (NodeJS, Python, Rust, Go, or Generic).
  - Retrieves active model name.
  - Counts pinned context files, character budgets, and workspace tree sizes.
  - Displays this information in a beautiful Rich Table and Panel.
* Integrated into: agent startup block in `ultron/cli.py` and the slash command router in `ultron/repl.py`.

--------------------------------------------------------------------------------
2. SLASH COMMAND ROUTING ENGINE & LOGS
--------------------------------------------------------------------------------
To build a faster, more developer-friendly workspace loop:
* Implemented slash commands:
  - `/workspace`: Prints the workspace status dashboard; blocks security-violating path switching.
  - `/status`: Prints the workspace status dashboard.
  - `/tree`: Prints the current directory structure.
  - `/refresh`: Clears and rebuilds the directory tree and index metadata cache.
  - `/logs [count]`: Displays the command history log (command line, exit code, stdout, and stderr) of recent executions.
* Integration: Registered in `UltronCompleter` for command completion and routed in `UltronREPL.handle_slash_command`.

--------------------------------------------------------------------------------
3. EXECUTION CONTROLS & PROCESS CANCELATION
--------------------------------------------------------------------------------
To prevent stuck tasks and safely retry commands:
* Implemented: `/last-error`, `/repeat`, and `/cancel`.
* How they work:
  - `/last-error`: Displays full trace logs and error output of the most recent execution failure.
  - `/repeat`: Repeats the last natural language prompt. Enforces a mutating safety guard: if the previous task modified workspace files, warns the user and requires explicit approval before re-executing.
  - `/cancel` / Ctrl+C Process Group Termination:
    - Starts subprocesses using `subprocess.Popen` in a new process group (`subprocess.CREATE_NEW_PROCESS_GROUP` on Windows, `os.setsid` on Unix).
    - Tracks executing process handles in `self.tools.current_process`.
    - If Ctrl+C or `/cancel` is triggered, cleanly terminates the entire process group (sending `CTRL_BREAK_EVENT` on Windows, `SIGKILL` on Unix PGID).
    - Sets `self.tools.last_error = "Command was cancelled by the user."`.

--------------------------------------------------------------------------------
4. DETERMINISTIC ONBOARDING SCANNERS
--------------------------------------------------------------------------------
To automatically index project settings without risking repository pollution:
* Implemented: `ProjectMemoryManager` in `ultron/onboard.py`.
* How it works:
  - Computes an MD5 hash of the workspace path.
  - Stores all settings outside the workspace in `~/.ultron/workspaces/<hash>/project_memory.json` to keep git working trees pristine.
  - Scans manifest configurations: `package.json` (NodeJS), `pyproject.toml` / `requirements.txt` (Python), `Cargo.toml` (Rust), `go.mod` (Go), or `Makefile` (C/C++).
  - Collects build, test, lint, formatting, and start commands.
  - Queries local Ollama (if available) for an architectural summary; falls back gracefully to a fully functional offline mode when Ollama is offline.
  - Initially flags newly discovered commands as `unverified`.

--------------------------------------------------------------------------------
5. COMMAND INTELLIGENCE & SAFETY GUARDS
--------------------------------------------------------------------------------
To protect system health and prevent unintended operations:
* Implemented: `is_side_effect_command` check in `ultron/security.py`.
* How it works:
  - Detects commands that install dependencies, run migrations, launch servers, access network resources, or perform destructive file operations.
  - If a command has side effects, enforces a mandatory confirmation prompt to the developer even if `auto_approve` is enabled.
* Command Verification:
  - If a command is marked `unverified` in project memory, warns the user and prompts for confirmation before execution.
  - If the command runs and succeeds (exit code 0), promotes it to `verified` in project memory so subsequent runs bypass the warning.

--------------------------------------------------------------------------------
6. WORKFLOW ORCHESTRATION & MULTI-FILE PLAN GUARDS
--------------------------------------------------------------------------------
To enforce technical designs for complex tasks:
* Implemented: `/plan <task>`, `/tasks` checklists, and planning constraints in `agent.py`.
* How they work:
  - `/plan`: Generates a technical design outline using the local model.
  - Planning guard: If the agent attempts to modify a second file without an active plan, blocks the execution and requires `/plan` to be formulated.
  - `/tasks [add|check|edit|test|clear]`: Manages a session-wide task list stored globally in `~/.ultron/workspaces/<hash>/tasks.json`.
  - Smart completion summary: Prints a structured box summarizing files modified, subprocesses executed, and warning staging locks when the task finishes.

--------------------------------------------------------------------------------
7. PHASE 1 VERIFICATION & SUCCESS RATE
--------------------------------------------------------------------------------
We added 6 new test categories verifying Phase 1 capabilities:
1. `test_workspace_command_disabled_switching`: Path switching is disabled for security.
2. `test_repeat_requires_confirmation_on_mutation`: Warns and prompts on mutating repeats.
3. `test_onboard_works_when_ollama_offline`: Validates deterministic scan when LLM is offline.
4. `test_command_status_unverified_to_verified_on_success`: Promotes commands upon success.
5. `test_project_runtime_data_git_clean`: Verifies global storage leaves git status pristine.
6. `test_cancel_long_running_process`: Validates process group cancellation and last_error tracking.

All tests passed successfully on Windows with an OK exit status (14/14 tests passing).

--------------------------------------------------------------------------------
1. REPOSITORY INDEXER (ultron/repo_map.py) - NEW FILE
--------------------------------------------------------------------------------
Created a full workspace indexer that builds a compact in-memory + disk-cached
map of the codebase without any external dependencies (pure regex-based).

What it does:
* Walks the workspace and indexes all code files (.py, .js, .ts, .go, .rs, etc.)
* Extracts symbols (classes, functions, methods, interfaces, structs) with line numbers
* Extracts imports per language using language-specific regex patterns
* Detects test files by name patterns (test_*, *_test.py, *.test.ts, etc.)
* Caches the index to ~/.ultron/repo_map/<hash>/index.json
* Incremental refresh: only re-indexes files whose mtime has changed

Key methods exposed:
- build(force)          → Walk and index workspace, return count of indexed files
- refresh()             → Incremental re-index (changed files only)
- find_symbol(name)     → Find symbol definitions by name (case-insensitive substring)
- find_references(sym)  → Find all files/lines referencing a symbol
- find_text(query)      → Regex text search across all indexed files
- get_file_symbols(f)   → All symbols defined in a file
- get_imports(f)        → All imports in a file
- get_test_files()      → List of all test files in index
- find_related_tests(f) → Test files related to a source file by name matching
- callers_of(sym)       → Call sites of a symbol (excluding its definition file)
- who_imports(f)        → Files that import from a given module
- get_summary()         → Total files, by-language counts, test file count

Ignored dirs: .git, node_modules, __pycache__, .venv, venv, build, dist,
target, vendor, .pytest_cache, .mypy_cache, .idea, .vscode, *.egg-info

--------------------------------------------------------------------------------
2. PROJECT ANALYZER (ultron/analyzer.py) - NEW FILE
--------------------------------------------------------------------------------
Contains four distinct capabilities:

A. ImpactAnalyzer
   Performs impact analysis on a file or symbol before making changes.
   - analyze_file(rel_path): returns symbols defined, callers, imported_by,
     related tests, risk level (low/medium/high), and warnings
   - analyze_symbol(symbol): returns definitions, callers, references, test
     coverage, risk level, and warnings
   - Risk is HIGH if imported by >5 modules or >10 callers
   - Warns if no related tests are found

B. FailureInvestigator
   Extracts actionable information from noisy error logs.
   - extract_errors(log): pulls meaningful error lines using 9 regex patterns
     covering Python tracebacks, pytest failures, Node/JS errors, Go failures,
     Rust compiler errors, and generic compiler-style errors
   - find_source_locations(log): extracts file:line references and resolves
     them to actual workspace files
   - investigate(log): full report with error_type classification
     (test_failure, syntax_error, import_error, runtime_error, compile_error,
     build_error), extracted errors, source locations, and repair suggestions
   - generate_min_repro(log): generates a minimal reproduction script,
     using the LLM if available, or a structured template as fallback

C. ConventionFinder
   Helps Ultron match existing code conventions before scaffolding new code.
   - find_similar_files(description): scores files by keyword match in path
     and symbol names, returns top matches
   - read_conventions(rel_path): reads first 40 lines of a file for style study
   - get_project_conventions(description): returns similar files + snippets
     with advice to study them before writing new code

D. ULTRON.md + .ultron.toml support
   - load_project_instructions(workspace): reads ULTRON.md (project instructions,
     capped at 3000 chars) and .ultron.toml (settings, capped at 2000 chars)
     and returns a formatted block injected into every system prompt
   - create_ultron_md_template(): scaffolds a blank ULTRON.md with sections for
     overview, architecture, conventions, pitfalls, and verified commands
   - create_ultron_toml_template(): scaffolds .ultron.toml with [project],
     [commands], [context], and [permissions] sections

E. Workspace discovery
   - find_folders(name, root): walks from a root, skipping .git, node_modules,
     system dirs, returns folders matching name (case-insensitive substring)

================================================================================
           ULTRON CLI - PHASE 3 (SAFE AUTONOMOUS ENGINEERING) REPORT
================================================================================

This section details the complete engineering, implementation, and verification
procedures executed for Phase 3 of the Ultron CLI.
All 10 user corrections from the planning review were incorporated before
implementation began (including 2 P0 fixes, 2 P1 fixes, and 6 design changes).

--------------------------------------------------------------------------------
1. SHARED COMMAND RUNNER (ultron/tools.py) - MODIFIED
--------------------------------------------------------------------------------
PROBLEM (P0): Verifier called self.tools.run_command() directly, bypassing the
approval enforcement in agent.py. /run, /commit, and other REPL commands could
also bypass _enforce_intent_mode() by calling run_command() directly.

SOLUTION: Added execute_command_with_policy() as the single authorized subprocess
gateway used by the agent, REPL, and Verifier. No code in Ultron spawns a
subprocess without going through this method.

What it does:
* Shows command + context label and calls Confirm.ask() when require_approval=True
* Returns {stdout, stderr, exit_code, truncated} dict (never a raw string)
* If the user declines -> returns {exit_code: -1, stderr: "Declined by user."}
* Applies the same timeout (180s), process-group termination, and output limit
  (6000 chars) as the legacy run_command(), keeping all behavior consistent
* Appends every run to tools.execution_logs regardless of exit code or approval
* Sets tools.last_error if exit code != 0

Additional change: Moved Confirm and time to module-level imports so they
can be properly patched in unit tests (lazy "from ... import" inside the method
made patch targets unresolvable in Python 3.14).

--------------------------------------------------------------------------------
2. INTENT MODE SYSTEM (ultron/agent.py + ultron/repl.py) - MODIFIED
--------------------------------------------------------------------------------
PROBLEM (P0): /run, /commit, and other REPL commands could bypass
_enforce_intent_mode() because mode enforcement only existed at the model
tool-dispatch layer inside agent.py, not at the REPL slash-command routing layer.

SOLUTION: Dual-layer enforcement - agent tool dispatch + REPL command routing.

agent.py additions:
* VALID_MODES = {"ask", "plan", "build", "fix", "review"}
* _MODE_BLOCKED_TOOLS dict: maps each mode to its forbidden tool set
* _enforce_intent_mode(tool_name): called at the TOP of
  _execute_tool_with_confirmation before ANY other logic; returns a refusal
  string or None
* Mode description injected into _get_system_message() so the LLM knows its
  mode and will not attempt forbidden operations

Blocked tools per mode:
  ask    -> write_file, patch_file, git_commit, run_command
  plan   -> write_file, patch_file, git_commit, run_command
  build  -> (none - default, fully capable)
  fix    -> (none - focused repair, fully capable)
  review -> write_file, patch_file, git_commit

repl.py additions:
* _REPL_MUTATION_COMMANDS dict: maps slash commands to their tool equivalents
* _enforce_repl_mode(cmd): checks the equivalent tool against _enforce_intent_mode()
  before executing /run, /commit, /test, /lint, /fix
* _get_mode_prompt(): prompt bar now shows active mode - [BUILD] ultron >
* New command: /mode <name> - switches mode at runtime, validates against VALID_MODES

Default mode is "build" -> fully backwards compatible; existing workflows unchanged.

--------------------------------------------------------------------------------
3. CHANGE CONTRACT ENGINE (ultron/contract.py) - NEW FILE
--------------------------------------------------------------------------------
A formal scope contract created before any multi-file autonomous task.

ChangeContract dataclass fields:
  goal                 Non-empty string describing the task objective
  preserved_behaviors  List of behaviors that must not break
  new_behaviors        List of behaviors the task must introduce
  expected_files       Relative workspace paths the task may touch
  verification_steps   Commands or checks to confirm task success
  completed_touches    Files actually written so far (grows at runtime)
  status               draft | active | completed | abandoned
  evidence             Verification results attached at completion

ChangeContractManager:
* validate_plan(plan): enforces schema - goal, expected_files (non-empty),
  verification_steps (non-empty), new_behaviors (non-empty); raises ValueError
  on failure so the agent must request a corrected plan first
* new_contract(plan): validates then persists to
  ~/.ultron/contracts/<workspace_hash>/active.json (outside workspace, git-clean)
* check_before_write(path): called BEFORE every file write in
  _execute_tool_with_confirmation():
    "allow"  -> file is in expected_files
    "ask"    -> file is new, policy == "ask", total files < max_files
    "block"  -> max_files ceiling reached, or policy == "block"
* approve_unplanned_file(path): adds user-approved file and re-persists
* record_completed_touch(path): called after every successful write
* complete_contract(evidence): marks status=completed with verification evidence
* display(console): /contract command renders the active contract as a Rich panel
* clear(): abandons and removes from disk

Configurable per project via .ultron.toml [contracts] section:
  max_files = 8                    (default - configurable per project)
  unplanned_file_policy = "ask"    (or "block")

Legacy guard retained: when no active contract is present, the original
multi-file /plan guard still applies (backwards compatibility).

Integration in agent.py:
* _load_toml_config(): minimal TOML parser to read [contracts] section
* ChangeContractManager instantiated in __init__ with toml_config
* check_before_write() called before checkpoint.start_task() in every write
* record_completed_touch() + evidence append called after every successful write

.ultron.toml template updated with [contracts] section documentation.

--------------------------------------------------------------------------------
4. VERIFICATION GATE (ultron/verifier.py) - NEW FILE
--------------------------------------------------------------------------------
Structured verification that runs read-only checks and produces a categorized
report. ALL commands dispatched via tools.execute_command_with_policy().

PROBLEM (P1): The original secret-check fallback used shell piping/grep which
is not portable to Windows.
SOLUTION: Secret scanning implemented entirely in Python regex via
CodeReviewer.run_static_checks() - no subprocess involved.

VerificationCheck fields: name, category, status, command, output, evidence
VerificationReport fields: timestamp, checks, overall (passed|failed|partial|not_run)

Status values:
  passed           -> command exited 0
  failed           -> command exited non-zero
  not_run          -> no command found for category
  skipped_by_user  -> user declined the Confirm prompt
  skipped_mode     -> category not allowed in current intent mode

Mode gating:
  READONLY_CATEGORIES = {"tests", "lint", "format_check", "typecheck"}
  In ask/plan mode: only READONLY_CATEGORIES run; "build" gets skipped_mode

Format safety:
  _ensure_check_flag(cmd): appends --check to ruff format, black, prettier
  commands to ensure format checks never mutate files

Command resolution priority:
  1. project_memory["commands"][category]["cmd"] (from /onboard or manual config)
  2. Ecosystem fallback: detects pytest.ini, package.json, Cargo.toml, go.mod, etc.
  3. Returns None -> status = not_run

Secrets category:
  Runs CodeReviewer.run_static_checks() on the current diff
  Filters security-tier findings only
  No subprocess launched - pure Python regex

Reports saved to ~/.ultron/verify/<hash>/<timestamp>.json
"Verified" shown ONLY when overall == "passed"

New command: /verify [checks...]
  e.g. /verify tests lint      -> runs those two checks only
       /verify                 -> runs all default checks
  If active contract present, verification evidence recorded in contract.

--------------------------------------------------------------------------------
5. SENIOR CODE REVIEWER (ultron/reviewer.py) - NEW FILE
--------------------------------------------------------------------------------
Three-tier structured diff analysis. No file mutations anywhere in this class.

IMPORTANT CLARIFICATION implemented per user correction:
  "Verified match" means the PATTERN MATCHED at that file:line location.
  It does NOT mean it is a confirmed bug. AI suggestions are NEVER labelled
  as confirmed defects - they are always prefixed with "Suggestion:".

Tier 1 - Verified match:  Regex matched at a specific file:line
Tier 2 - Heuristic:       Pattern-based, may have false positives
Tier 3 - AI suggestion:   Model opinion, "Suggestion:" prefix, never stored
                          as confirmed defects

Static checks (all Python regex - no subprocess/grep, Windows portable):
  security     -> hardcoded credentials/tokens (verified_match, critical)

7. EVIDENCE TAGS + CLARIFICATION GATE (ultron/agent.py) - MODIFIED
--------------------------------------------------------------------------------
PROBLEM (P1): needs_clarification=true combined with tool calls suppressed the
clarification gate - edits could execute despite an unresolved question.
SOLUTION: If structured output says clarification is needed, always pause and
execute NO tools. Treat "clarification + tool_calls" as invalid structured output
and discard all tool calls from that response.

Evidence tagging:
  EvidenceTag enum (str-based for display):
    OBSERVED     -> "Observed from code"  (file written/modified)
    VERIFIED     -> "Verified by command" (command exited 0)
    INFERRED     -> "Inferred"            (no command ran to confirm)
    NOT_VERIFIED -> "Not verified"        (explicit unverified conclusion)

  Task completion summary now shows evidence tags on every item:
    * auth/user.py  (Observed from code)
    * pytest tests/ -> Command exited with code 0  (Verified by command)

  Evidence-based completion line:
    If any _task_evidence entry is NOT_VERIFIED -> shows partial verification warning
    Otherwise -> shows "Task complete"

Clarification gate - _handle_clarification_gate(response_message):
  Structured path:
    Detects {"needs_clarification": true, "question": "..."} JSON in response
    If found and tool_calls are also present -> discards all tool_calls (logs warning)
    Returns question string -> REPL can pause for user input
  Fallback path (for models without structured output):
    If no tool_calls AND response ends with a '?' sentence -> treats as question
    If tool_calls are present -> fallback does NOT trigger
  Returns None -> no clarification needed, continue normally
