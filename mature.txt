# Ultron Maturity, Reasoning, and Flexibility Plan

Purpose: Turn Ultron from a capable local coding CLI into a trusted software-engineering teammate. This plan complements phases.txt. It focuses on how Ultron reasons, how it adapts to projects and models, and how the team proves it is reliable.

====================================================================
MATURITY MODEL
====================================================================

Level 1 - Safe assistant
Ultron cannot escape its workspace, overwrite user work silently, execute malformed calls, or claim unverified success.

Level 2 - Project-aware developer tool
Ultron understands the active repository, its commands, conventions, tests, and major code paths.

Level 3 - Controlled coding agent
Ultron plans, edits, tests, fixes, reviews, and stops safely when a task becomes ambiguous or exceeds its intended scope.

Level 4 - Flexible engineering platform
Ultron works across programming languages, project types, model providers, developer tools, and team workflows.

Level 5 - Trusted developer teammate
Ultron is evaluated continuously against realistic coding tasks and earns confidence through measurable results.

====================================================================
WORKSTREAM A - STRUCTURED ENGINEERING REASONING
====================================================================

Goal: Prevent the model from jumping directly from a request to edits. Every non-trivial task follows a visible engineering workflow.

Required task lifecycle:

1. Understand
   - Classify the request: ask, analyze, debug, feature, refactor, test, review, or project setup.
   - Identify unclear requirements, constraints, affected systems, and desired outcome.
   - Ask one concise question only when the missing answer materially changes the implementation.

2. Inspect
   - Read project instructions, Git status, project map, relevant source files, related tests, and recent error output.
   - Do not edit before enough relevant evidence has been collected.

3. Plan
   - Record target files, expected behavior, preserved behavior, risks, intended tests, and estimated change scope.
   - Use read-only /plan for plans that the developer wants to review first.

4. Assess impact
   - Find references, callers, imports, related tests, public APIs, schemas, database effects, and external contracts.
   - Warn before public API changes, destructive data changes, security-sensitive changes, or scope growth.

5. Execute
   - Create a checkpoint before the first mutation.
   - Prefer the smallest coherent patch.
   - Follow existing patterns in the project rather than generic generated structures.
   - Enforce the configured approval policy before risky tool actions.

6. Verify
   - Run focused tests first, then lint/type/build/full tests when appropriate.
   - Parse failures, investigate evidence, and make bounded repair attempts.
   - Do not loop indefinitely; stop after a configured attempt budget and summarize the blocker.

7. Review and handoff
   - Review the final diff for bugs, security risks, missing tests, compatibility issues, and accidental scope.
   - Provide changed files, commands run, observed results, unverified work, risks, and next steps.

Implementation plan:

- Add a Task model with id, intent, mode, status, plan, expected_files, actual_files, risks, verification_steps, evidence, and checkpoint_id.
- Add a TaskRouter that selects a workflow template from the detected request intent.
- Add task statuses: planned, inspecting, editing, testing, blocked, verified, cancelled.
- Add a bounded retry policy: maximum repair attempts, time budget, and tool-call budget per task.
- Render each task state clearly in the REPL status line and /tasks command.
- Add evidence labels to final summaries: Observed from code, Verified by command, Inferred, Not verified.

Acceptance criteria:

- A feature task produces a plan before the first mutation.
- A bug-fix task identifies a failing reproduction before claiming success.
- A task stops and asks before exceeding its agreed change budget.
- Every completion summary distinguishes verified facts from assumptions.

====================================================================
WORKSTREAM B - PROJECT INTELLIGENCE
====================================================================

Goal: Make the agent smart because it understands the active repository, not because it blindly receives more prompt text.

Capabilities:

1. Project onboarding
   - Detect language, framework, package manager, entry points, tests, lint, formatter, type checker, build, migrations, services, and common run commands.
   - Store verified facts in project memory, but re-check facts when they become stale.

2. Repository map
   - Create a compact indexed representation of files, packages, symbols, imports, tests, routes, configuration, and dependencies.
   - Exclude ignored/generated/dependency directories.
   - Refresh incrementally after files change rather than rebuilding on every turn.

3. Code navigation
   - Support finding text, symbols, definitions, references, feature/data flow, and related tests.
   - Provide file paths and evidence for every answer.

4. Impact analysis
   - Map a requested change to callers, imports, public endpoints, schemas, database models, migrations, feature flags, and tests.
   - Identify change risk before editing.

5. Failure investigation
   - Extract actionable errors from noisy logs.
   - Link stack traces to project files and likely root causes.
   - Create minimal reproductions and regression tests before broad fixes where practical.

6. Convention-aware generation
   - Locate examples of similar functionality before adding files or code.
   - Reuse naming, folder layout, validation, error handling, dependency injection, and test conventions.

Implementation plan:

- Add a ProjectProfile service to inspect manifest files and configured commands.
- Add a RepositoryIndex interface, first implemented with safe file walking plus regex; later add tree-sitter and LSP adapters for language-aware symbols/references.
- Store per-workspace cache data outside the repository and invalidate entries from changed file paths.
- Add commands: /onboard, /find, /symbol, /references, /flow, /explain, /impact, /why, and /min-repro.
- Add ULTRON.md for project instructions and .ultron.toml for commands, project rules, context budget, and permissions.

Acceptance criteria:

- In an unfamiliar project, Ultron finds the entry point, test command, and code responsible for a named feature.
- /impact identifies relevant callers and tests before a public method is changed.
- /why reduces long failing logs to the meaningful error, source location, and proposed next step.

====================================================================
WORKSTREAM C - RELIABLE TOOL USE AND CONTROLLED AUTONOMY
====================================================================

Goal: Let Ultron act independently inside safe, observable boundaries.

Capabilities:

- Per-tool, per-path, per-command, and later per-network permission rules: allow, ask, deny.
- Risk labels for every action: read-only, workspace write, Git write, package install, network, destructive.
- Typed tool schemas, strict validation, output limits, timeouts, cancellation, and structured failures.
- Checkpoint-aware edits, conflict-aware undo, scoped Git staging, and task-level commits.
- Change budget that pauses when actual scope differs materially from expected scope.
- Read-only ask/plan/review modes and controlled build/fix modes.
- Bounded retry/recovery behavior that stops instead of repeatedly attempting unsafe or failing commands.

Implementation plan:

- Replace ad-hoc tool dispatch with a ToolRegistry containing name, schema, risk level, permission requirements, executor, and output policy.
- Add a PolicyEngine that evaluates current workspace, path, command, and user-selected approval mode.
- Persist approval decisions only when the user explicitly requests a reusable rule.
- Add a CommandRunner with structured result fields: command, cwd, exit_code, stdout, stderr, duration, timed_out, truncated, cancelled.
- Add a ChangeTracker that records expected/actual files, file hashes, Git state, checkpoints, and user-dirty files.
- Add modes: /ask, /plan, /build, /fix, /review.

Acceptance criteria:

- Every tool call has a validated schema and visible risk level.
- User work is never silently committed, reverted, or overwritten.
- A tool failure is returned to the model as structured evidence and does not crash the session.
- A stuck repair task stops under its configured budget and leaves a clear handoff.

====================================================================
WORKSTREAM D - MODEL AND PLATFORM FLEXIBILITY
====================================================================

Goal: Avoid coupling Ultron's workflow quality to one API or one model.

Provider architecture:

ModelProvider interface:
- list_models()
- health_check()
- capabilities()
- chat(messages, tools, settings, stream)
- count_or_estimate_tokens()
- normalize_tool_calls()

Initial providers:
- OllamaProvider
- OpenAICompatibleProvider

Future optional providers:
- AnthropicProvider
- GeminiProvider
- LMStudioProvider
- OpenRouterProvider

Model capability metadata:
- context window
- streaming support
- native tool-call support
- reasoning support
- vision support
- cost/latency profile when available

Routing policy:
- Fast/local model: repository map, file discovery, log summarization, lightweight classification.
- Strong coding model: implementation plans, complex edits, debugging, and review.
- Low-cost model: commit messages, changelog/PR summaries, and repetitive transformations.
- Always disclose the active model and let the user override it.

Implementation plan:

- Keep Ollama behavior behind the provider interface before adding any second provider.
- Move provider-specific payload logic out of agent.py.
- Add model profiles in user and project configuration.
- Add /models, /model, and /model-info commands.
- Maintain a capability fallback path for models without native tools: validated textual tool-call protocol only.

Acceptance criteria:

- Switching providers does not change tool safety, task lifecycle, checkpoint behavior, or project context behavior.
- A model that lacks native tools cannot cause malformed textual calls to execute.

====================================================================
WORKSTREAM E - ENGINEERING QUALITY FEATURES
====================================================================

Goal: Help developers find and prevent defects, not only write code faster.

Capabilities:

- /verify: focused tests, full test suite when appropriate, lint, formatting, type checking, build, secret scan, and diff review.
- /review: bugs, security, performance, authorization, public API, test gaps, dead code, and duplication review.
- Test-gap finder: identify changed code paths without matching tests.
- Refactor guard: references, impact, checkpoint, small edits, focused verification, compatibility report.
- /trace: trace feature flow through route, service, domain, persistence, and tests.
- /compare: compare working/broken branches or versions.
- /flaky-test: rerun a test, collect variation evidence, and preserve reproduction data.
- /bisect guidance: help identify the commit that introduced a regression.
- /doctor: validate runtime, dependencies, environment requirements, ports, configured services, and project startup assumptions.
- Optional configured dependency and security audit commands.

Implementation plan:

- Add a VerificationPlanner that selects commands from ProjectProfile and changed-file impact.
- Implement report parsers for pytest, unittest, npm, cargo, go test, common linters, and type checkers incrementally.
- Store verification results as structured Task evidence.
- Add pluggable language/project analyzers instead of putting all detection logic in one module.
- Start with deterministic checks; do not claim deep static-analysis guarantees until a language-aware analyzer supports them.

Acceptance criteria:

- /verify reports exactly which checks passed, failed, were skipped, or were not run.
- /review references source/diff locations and does not present speculation as a confirmed defect.
- A refactor task checks references and focused tests before reporting completion.

====================================================================
WORKSTREAM F - MEASUREMENT AND CONTINUOUS MATURITY
====================================================================

Goal: Prove Ultron improves over time with data, reproducible tests, and real developer feedback.

Evaluation suite:

1. Workspace safety
   - traversal, sibling, symlink/junction, multi-drive, sensitive path, and malformed-tool tests.

2. Git safety
   - dirty worktree, dirty same-file, scoped commit, undo conflict, created-file undo, and task checkpoint tests.

3. Core coding tasks
   - fix a failing validation test
   - add a small endpoint with tests
   - safely rename a symbol across references
   - diagnose a traceback and add a regression test
   - modify a multi-package project with focused tests

4. Agent behavior
   - task planning before edits
   - bounded retry behavior
   - refusal to claim success without verification
   - correct handling of unavailable model/server

Metrics:

- task completion rate
- post-change test pass rate
- regression rate
- unsafe tool/action rate
- incorrect success-claim rate
- unnecessary files changed
- time to first useful diagnosis
- tool failure recovery rate
- approval friction (approvals per successful task)
- context overflow/compaction rate

Implementation plan:

- Build a deterministic mock-provider test harness first.
- Add fixture repositories for Python, Node, Go, Rust, and monorepo scenarios.
- Record task actions and evidence locally with source-code recording disabled by default.
- Run the suite in CI before releases.
- Use failures to add regression tests before adding more features.

Acceptance criteria:

- Every serious defect becomes a reproducible regression test.
- Releases publish test/evaluation results and known limitations.
- The team can compare Ultron versions with the same task set.

====================================================================
RECOMMENDED IMPLEMENTATION ORDER
====================================================================

1. Complete phases.txt Phase 0: safety, Git, checkpoints, bounded context, and tests.
2. Build Task, TaskRouter, ToolRegistry, PolicyEngine, CommandRunner, and ChangeTracker as internal foundations.
3. Add ProjectProfile, onboarding, command intelligence, repository map, and /why.
4. Add /plan, /tasks, /test, /fix, /verify, review, evidence summaries, and change budgets.
5. Refactor Ollama into the provider interface; add OpenAI-compatible support only after the abstraction is tested.
6. Add language-aware navigation, impact/refactor tooling, and quality analyzers incrementally.
7. Add worktrees, handoff, CI/headless workflow, and coding-focused integrations.
8. Continuously expand evaluation fixtures and promote only measured, reliable features to default behavior.

Definition of mature:

Ultron is mature when developers can trust it to work inside the selected workspace, understand a project before editing it, make small evidence-backed changes, protect existing work, recover from failures, and provide a clear verified handoff across real projects and model providers.
